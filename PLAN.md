# PLAN — Club Planner Desktop

Статус: этапы 16–36 и публичный Windows-релиз `v0.2.3` завершены. Реализованы ручная магнитная трассировка прямых/дуг, улучшенное распознавание и плавное композитное панорамирование без корневого React-render на каждом событии мыши. Frontend/benchmark/Rust/rendered/Windows gates пройдены; подписанные updater-артефакты опубликованы. Внешними открытыми доказательствами остаются отдельная clean Windows 10/11 VM и лицензированный реальный holdout, отличный от предоставленного пользователем локального плана.

## Этап 36: плавное панорамирование холста · P0 · завершён

### Диагноз

Текущий `BasePlanCanvas` вызывает корневой `setCamera` на каждом `pointermove` при зажатой ПКМ. Изменение `camera` заставляет React повторно пройти `App`, боковую панель и большой SVG-граф, пересчитать zoom-зависимые handles/размеры и запустить эффект видимого центра. Частота pointer-событий может быть выше частоты экрана, поэтому очередь React/DOM-коммитов отстаёт от курсора даже на мощном ПК.

### Исправление

1. Во время pan хранить промежуточную камеру в `ref`, не в React state.
2. Обновлять только композитный CSS `transform` корневого SVG-слоя через один `requestAnimationFrame`; более частые события объединять в последний кадр.
3. На `pointerup`/`pointercancel` сделать ровно один `onCameraChange`, чтобы синхронизировать `App`, видимый центр и последующее добавление объектов.
4. Не менять семантику ПКМ: короткий клик открывает меню, drag подавляет меню; `Shift+ПКМ` остаётся группировкой, средняя кнопка и `Пробел+ЛКМ` используют тот же быстрый путь.
5. На размонтировании отменять запланированный кадр и не оставлять временный transform/cursor state.

### Проверки

- component-тест отправляет серию `pointermove` и подтверждает отсутствие React camera-коммитов до отпускания и ровно один итоговый коммит;
- итоговая камера и SVG-transform совпадают с последней позицией курсора;
- короткий ПКМ, `Shift+ПКМ`, pointer capture и context-menu suppression не регрессируют;
- `pnpm check`, Rust fmt/test/Clippy, rendered desktop QA, portable/NSIS smoke;
- версия `0.2.3`, обновлённые EXE/updater-артефакты и публичный release после зелёных gates — пройдено workflow `32387883068`.

Gate: панорамирование визуально следует за курсором без очереди React-render; N событий перемещения создают не более одного DOM-write на display frame и один React camera-коммит за жест.

## План этапов 29–35: ручная магнитная трассировка и восстановление пропущенных стен

Цель — гарантировать, что любой импортированный план можно точно довести до рабочего состояния прямо на этапе проверки, даже если автоматическое распознавание пропустило часть геометрии. Ручное исправление поставляется раньше следующей попытки повысить recall: пользователь не должен ждать идеального CV-алгоритма, чтобы завершить план.

### Диагноз по предоставленному экрану

На принятом для аудита экране мастер показывает `68 стен`, `0 принято`, `0 проёмов` и `48 проблем`. Основные наблюдения:

- крупные прямые стены распознаны фрагментарно; короткие участки, стены с окнами/разрывами и часть внутренних перегородок пропущены;
- левый криволинейный фасад полностью отсутствует в архитектурном слое;
- зелёные и жёлтые линии закрывают часть исходного чертежа, но не объясняют, какой штрих подложки был использован как свидетельство;
- кнопки `Стена · 2 точки` и `Дуга · 3 точки` уже существуют, но текущее поведение не похоже на полноценное черчение: нет живого preview, магнитной привязки, указания активного режима, длины/угла под курсором, непрерывной цепочки и понятного удаления;
- текущий `addManualWall` всегда создаёт две новые вершины. Даже при точном клике по существующему узлу новая стена топологически остаётся отсоединённой;
- после второй/третьей точки инструмент автоматически выключается, поэтому восстановление длинного контура требует повторно нажимать кнопку для каждого сегмента;
- ручной участок можно отклонить через общий review-механизм, но нет явной команды `Удалить стену` и понятного поведения для связанных проёмов;
- точное попадание затруднено отсутствием zoom-at-cursor/pan в review-холсте;
- `detectArcs` по умолчанию выключен, а текущий raster-путь ищет полные окружности `HoughCircles` и принимает стену только после нахождения совместимой концентрической пары. На прерывистом фасаде с окнами и надписями такая пара не формируется.

### Зафиксированный пользовательский сценарий

1. Пользователь выбирает режим `Стена`.
2. Подводит курсор к началу стены на подложке; ближайший существующий узел или направляющая подсвечивается, а точка магнитится в экранном радиусе.
3. Первый клик фиксирует начало.
4. При движении курсора показываются полупрозрачная стена реальной толщины, осевая линия, длина, угол и тип активной привязки.
5. Направление пытается совпасть с линией исходного чертежа либо продолжением существующей стены. `Tab` перебирает близкие варианты, `Alt` временно отключает магнит, `Shift` фиксирует ортогональный/угловой режим.
6. Второй клик создаёт и сразу принимает стену одной Undo/Redo-транзакцией. Если конец попал в существующий узел, используется его ID; если попал в середину стены, эта стена корректно разделяется и образуется общий узел.
7. По умолчанию начинается следующий сегмент из только что созданной конечной точки. `Esc` завершает цепочку, правый клик отменяет текущий незавершённый сегмент.
8. Пользователь может выбрать ошибочную стену и нажать `Delete` либо кнопку `Удалить`; `Ctrl+Z` полностью восстанавливает стену и связанные данные.

Для дуги используется понятная трёхточечная схема: первый клик — начало, второй — конец хорды, движение курсора показывает кривизну, третий клик на контуре фиксирует сторону и радиус. Если под подложкой найден подходящий криволинейный guide, preview притягивается к нему целиком, а не только отдельными точками.

### Правила магнитной привязки

Все пороги задаются в экранных пикселях, чтобы поведение не менялось при zoom:

- захват кандидата: `10 px`, отпускание уже выбранного кандидата: `16 px` — гистерезис не даёт preview дрожать;
- дополнительный метрический предел: не дальше `0,25 м` от сырой точки указателя;
- приоритет: `существующий узел → пересечение/точка на существующей стене → подтверждённая ось стены на подложке → одиночный source-guide → ограничение угла → сетка`;
- snapping никогда не изменяет уже созданную геометрию без preview и второго клика;
- маркер сообщает источник: `узел`, `пересечение`, `ось стены`, `линия подложки`, `касательная`, `угол 90°`;
- `Alt` отключает все привязки, `Tab` циклически выбирает кандидата, `Shift` фиксирует угол с шагом 15° и отдельно предпочитает 0/45/90°;
- кандидат оценивается по расстоянию до курсора, разнице угла, непрерывности тёмных пикселей, длине поддержки, наличию парных граней, близости пересечения и штрафам за текст/штриховку;
- активный snap хранится до выхода за release-порог, а не выбирается заново на каждом `pointermove`.

### Данные направляющих

Финальный архитектурный граф и чертёжные подсказки должны быть разными слоями:

- `RecognitionDraft.walls` остаётся только редактируемой архитектурой;
- новый временный `RecognitionGuideSet` хранит прямые guide-сегменты, цепочки контуров, fitted arcs, пересечения, тип свидетельства и confidence в координатах исходника;
- guide-слой формируется из расширенного набора `rawLines`, пар граней, локальных контуров и PDF-paths до строгой фильтрации архитектуры;
- guide не сохраняется как стена и не влияет на 2D/3D, помещения или проверки, пока пользователь явно не создаст по нему архитектурную сущность;
- в review UI guide-слой по умолчанию почти невидим и подсвечивается только рядом с курсором; отдельный переключатель позволяет показать все подсказки для диагностики;
- исходная картинка остаётся заблокированной, с регулируемой прозрачностью; ручные стены сохраняются в метрах и с `provenance: manual`.

### Этап 32 — магнитная дуга и автоматические кривые · P0/P1 · основной сценарий реализован

Не усиливать только `HoughCircles`: он ищет параметры полной окружности и чувствителен к выбранным порогам/разрывам. Вместо этого:

- получать связные edge chains через `findContours`, разрывать их в угловых точках и упрощать с контролируемой погрешностью;
- robust circle fit/RANSAC применять к локальной цепочке, а не ко всему изображению; хранить остаточную ошибку, angular coverage, gap ratio и gradient support;
- искать парные концентрические цепочки с согласованной толщиной и перекрытием по углу; ось стены строить по среднему радиусу;
- если фасад не является одной окружностью, сегментировать его на минимальное число совместимых straight/arc частей с общей касательной и общими вершинами;
- автоматом создавать только высокоуверенную парную дугу; одиночные fitted arcs остаются magnetic guides для ручной трассировки;
- в ручном режиме использовать `начало → конец хорды → точка кривизны`, показывать радиус, длину дуги и направление;
- snap endpoints выполняется к узлам/стенам, а третья точка — к ближайшему curved guide; при нескольких дугах `Tab` переключает вариант;
- итог хранится существующим `bulge`; сегментированная кривая становится цепочкой bulge-дуг с общими вершинами.

Gate на пользовательском плане: левый фасад появляется хотя бы как корректная цепочка manual/magnetic arcs; автоматическая дуга разрешается только при средней ошибке оси не более `0,05 м` после калибровки и без ложных дуг в текстовых/лестничных областях.

Техническая опора: OpenCV предоставляет локальный `LineSegmentDetector`, контуры и `approxPolyDP` для построения направляющих, а текущий `HoughCircles` следует оставить только генератором гипотез, а не финальным классификатором стены: [LineSegmentDetector](https://docs.opencv.org/4.13.0/db/d73/classcv_1_1LineSegmentDetector.html), [контуры и аппроксимация](https://docs.opencv.org/4.x/d3/dc0/group__imgproc__shape.html), [Hough Circle Transform](https://docs.opencv.org/4.x/d4/d70/tutorial_hough_circle.html).

### Этап 33 — повышение recall прямых стен · P1 · реализован консервативный вариант

- объединить текущий `HoughLinesP` с `LineSegmentDetector` на 2–3 масштабах;
- оставить парные грани главным сильным доказательством, но разрешить topology-backed single-stroke wall, если линия продолжает подтверждённую стену, соединяет два архитектурных узла либо имеет устойчивую поддержку на нескольких масштабах;
- восстанавливать короткие закрытые текстом/размером gaps только при совпадении направления, толщины и пиксельной поддержки с обеих сторон;
- отдельно обрабатывать окна: наружная стена не должна исчезать из-за нескольких оконных разрывов;
- после построения выполнять component-level optimization: полезнее принять согласованный контур помещения, чем независимые зелёные фрагменты;
- confidence считать по фактическим признакам и калибровать на private holdout; длинная линия сама по себе не получает высокий confidence.

Gate: recall прямых стен на пользовательской private-разметке растёт без возврата `спагетти`; synthetic/разрешённые scan/photo gates не ухудшаются более чем на 0,01 F1.

### Этап 34 — безопасное удаление и топологические команды · P0 · реализован

- выделенная recognized-стена удаляется из рабочего графа через `reviewStatus: rejected`, чтобы её можно было восстановить и сохранить provenance;
- manual-стена удаляется физически вместе с неиспользуемыми вершинами; Undo возвращает те же IDs;
- при удалении host wall связанные двери/окна удаляются той же транзакцией либо, если возможно, перепривязываются только после явного preview;
- добавить `Удалить`, `Восстановить`, клавишу `Delete`, контекстное действие и подтверждение только при наличии связанных проёмов;
- вынести операции `add/split/connect/delete/restore` в чистые review-команды вместо прямого изменения массивов React-компонентом;
- после каждой команды пересчитывать issues/quality, но не отменять ручную операцию из-за неблокирующего предупреждения;
- selected wall показывает длину, угол, для дуги — радиус и sweep; изменение чисел является отдельной Undo-транзакцией.

Gate: add/delete/restore/split сохраняют валидный граф, не оставляют orphan vertices/openings и корректно работают после Undo/Redo.

### Этап 35 — тесты, документация и выпуск · P0 · завершён в v0.2.2

Unit-тесты:

- snap scoring, приоритеты, screen-space radius, hysteresis, `Alt`, `Shift`, `Tab`;
- screen/source/meter round-trip при zoom/pan;
- пересечение направляющих, projection на line/arc, reuse/split vertex;
- line-chain state machine и отмена незавершённого gesture;
- three-point bulge, curved-guide snap, concentric pair и piecewise arc fit;
- topology-backed single stroke и защита от размерных линий/штриховки;
- delete/reject/restore, orphan cleanup, связанные openings, Undo/Redo.

Интеграционные и rendered-сценарии:

1. Импорт фото → `Стена` → первый клик → live preview → magnetic second click → accepted wall.
2. Непрерывно дорисовать три сегмента комнаты, закончить `Esc`, отменить одной командой последний сегмент.
3. Подключить новую стену к середине существующей и получить общий T-узел.
4. Нарисовать дугу по кривому фасаду, изменить радиус, удалить и восстановить.
5. Zoom/pan во время трассировки не меняют метрические координаты.
6. `Alt` позволяет сознательно рисовать мимо ложной source-линии, `Tab` выбирает соседний guide.
7. Удаление recognized/manual стены и host wall с проёмом показывает правильный preview и историю.
8. Полностью довести предоставленный план до валидного графа без повторного распознавания.

Выпускной gate:

- `pnpm check`, Rust fmt/test/Clippy, recognition benchmark и новый curved-wall/manual-edit benchmark;
- визуальная проверка на предоставленном плане, разрешённом scan/photo corpus и чистой Windows 10/11;
- обновить `PRODUCT_SPEC`, `ACCEPTANCE_CRITERIA`, `ARCHITECTURE_DECISION`, `USER_GUIDE`, `QA_REPORT` и release notes;
- только после зелёных gates поднять версию, пересобрать portable/NSIS EXE, опубликовать подписанный релиз и проверить `latest.json`/`.sig`.

### Критерии готовности этой итерации

- пользователь явно видит и понимает активный инструмент;
- любая прямая стена создаётся двумя кликами с живым магнитным preview;
- дуга создаётся тремя кликами и может притянуться к кривой исходника;
- новая геометрия соединяется с существующим графом, а не только визуально касается его;
- ошибочную стену можно удалить и вернуть через Undo/Redo;
- пропущенные стены на предоставленном плане можно вручную восстановить без выхода из мастера;
- криволинейный фасад восстанавливается вручную с magnetic guides даже при отказе автоматики;
- автоматический recall растёт измеримо, без возврата ложных стен и дуг;
- все действия остаются локальными и не требуют сети.

### Риски и решения

| Риск | Решение | Gate |
|---|---|---|
| магнит цепляется к размерам или тексту | semantic masks, scoring по непрерывности/углу, явный marker, `Tab` и `Alt` | fixtures + rendered |
| snap дрожит между двумя линиями | screen-space hysteresis `10/16 px` и удержание active candidate | unit + pointer QA |
| визуальное касание создаёт разорванный граф | reuse vertex или atomic split existing wall | topology tests |
| фасад не является одной окружностью | piecewise line/arc fit с общими вершинами и tangent continuity | curved fixtures |
| слишком слабые дуги возвращают ложные окружности | одиночная дуга только guide; auto wall требует paired evidence и benchmark gate | false-arc gate |
| удаление стены портит проёмы | одна review-команда, cascade/preview и Undo с теми же IDs | command tests |
| точное черчение невозможно без увеличения | zoom-at-cursor, pan и единая координатная матрица | transform + rendered |
| большой guide-набор тормозит pointermove | spatial index, viewport query и preview вне React history | performance profile |

Рекомендуемая последовательность поставки: `29 → 30 → 31 → 34 → 32 → 33 → 35`. Прямая ручная трассировка и безопасное удаление являются P0 и должны быть выпущены раньше экспериментального автоматического повышения recall.

## План этапов 22–28: исправление и улучшение распознавания

Цель — заменить нынешнее распознавание «контрастный штрих → архитектурный кандидат» на проверяемый конвейер «семантически очищенное изображение → геометрические свидетельства → архитектурный граф → оценка качества». План составлен по регрессии на реальной фотографии обмерного плана: диагональная штриховка, размерные цепочки, цифры и цветные пометки были ошибочно приняты за стены и дуги, результат породил сотни свободных концов и стал непригоден для ручной проверки.

### Результат P0-итерации 2026-08-20

Реализовано:

- `pnpm recognition:benchmark` запускает PDF/raster detector и production graph builder на 30 версионированных эталонах, пишет JSON/Markdown/per-case SVG и завершает `check` ошибкой при нарушении выпускных порогов;
- корпус обновлён до manifest v2: стена через дверной проём хранится как единый host, фотографии содержат известную четырёхточечную перспективную калибровку;
- красные пользовательские пометки маскируются отдельно, синие условные обозначения дверей/окон извлекаются в собственный слой, мелкие text-like компоненты удаляются до Hough независимо от OCR-подсказок;
- регулярная диагональная штриховка исключается до парного анализа граней; одиночная длинная линия больше не становится стеной;
- прямые стены строятся из пар граней, цветной дверной разрыв объединяется в единый host wall, T/L/X-пересечения аналитически разделяются на общий топологический граф;
- общий raster `HoughCircles` больше не создаёт двери; raster-дуга может стать стеной только при концентрическом парном свидетельстве, а автоматическое raster-распознавание дуг по умолчанию отключено;
- добавлен `RecognitionQualityReport`, запрет пакетного принятия ненадёжного результата, порог «надёжного» кандидата 0,86 и ограничение визуализации candidate explosion;
- на синтетическом разрешённом корпусе подтверждены прямые стены: vector PDF F1 1,000; scan F1 0,984, opening F1 1,000; rectified photo F1 0,938, opening F1 0,950. Отчёт воспроизводится локально и не коммитит закрытые планы;
- на предоставленной пользователем фотографии аварийная регрессия устранена: вместо сотен дуг и 346 проблем формируется ограниченный редактируемый граф; результат честно получает статус `review`, пакетное принятие недоступно.
- frontend/Rust gates, rendered desktop QA, portable smoke и NSIS install/launch/uninstall пройдены; `v0.2.1` опубликован через авторизованный CI, подписанный updater-манифест и Windows-артефакты доступны в GitHub Releases.

Остаётся до полного закрытия этапов 22–28:

- отдельный измеримый curved-wall/arc gate: безопасная фильтрация реализована, но F1 настоящих raster-дуг ещё не подтверждён;
- private holdout из разрешённых реальных планов, разбиение development/holdout, p95/false-length/node/room метрики и калибровка confidence на нём;
- диагностические переключаемые маски и принятие связного компонента/помещения вместо отдельных высокоуверенных кандидатов;
- ручной offline smoke на отдельной чистой Windows 10/11 VM. До этих проверок нельзя переносить синтетические цифры на произвольные коммерческие планы.

### Зафиксированный дефект и исходная гипотеза

- `adaptiveThreshold` и `HoughLinesP` видят стены, штриховку, размерные линии, текст и стрелки как один бинарный слой;
- общий `HoughCircles` создаёт ложные дуги по тексту, пересечениям, цветным обводкам и фрагментам нескольких несвязанных линий;
- confidence сейчас в значительной мере растёт от длины прямой или угловой протяжённости дуги, поэтому ложная геометрия может окрашиваться зелёным;
- подходящие линии и дуги превращаются в стены до проверки связности, постоянства толщины и архитектурной правдоподобности;
- существующий `corpus:validate` проверяет manifest, лицензию, наличие ground truth и SHA-256, но не запускает распознаватель и не вычисляет precision/recall/F1;
- текущие 30 синтетических файлов полезны для детерминированной регрессии, но недостаточно представляют плотные размеры, штриховку, рукописные пометки, неполный кадр, сложные криволинейные стены и реальные дефекты фотографии.

Предоставленная пользователем фотография остаётся локальной ручной фикстурой. Не добавлять её или производные в публичный Git-репозиторий без отдельного разрешения на распространение.

### Принципы нового конвейера

1. Не восстанавливать отсутствующую часть обрезанного плана и не замыкать помещения выдуманной геометрией.
2. Локализация текста для маскирования выполняется независимо от пользовательской опции распознавания содержимого текста; выключение OCR-подсказок не должно возвращать цифры в слой стен.
3. Прямая стена требует геометрических свидетельств: две согласованные грани либо специально подтверждённая тонкая перегородка, а не просто длинный Hough-отрезок.
4. Дуговая стена и дуга открывания двери являются разными классами с разными признаками.
5. Confidence означает измеренную вероятность корректности на отложенном корпусе, а не длину примитива.
6. При низком качестве система честно отказывается от пакетного принятия и предлагает повторную обрезку, другой профиль либо ручную разметку.
7. Каждый промежуточный слой доступен в диагностическом режиме, чтобы ложное решение можно было воспроизвести и объяснить.

### Этап 22 — воспроизводимый benchmark и регрессионный корпус · P0

Задачи:

- реализовать headless-команду `recognition:benchmark`, которая запускает тот же PDF/raster pipeline, что и приложение, а не отдельную тестовую имитацию;
- сохранять для каждого случая версию движка, параметры, длительность, исходные кандидаты, итоговый граф и диагностические маски;
- реализовать метрическое сопоставление эталонных и найденных прямых/дуг по перекрытию, расстоянию между выборками кривых, углу и положению концов;
- считать отдельно precision/recall/F1 стен, дуговых стен, дверей и окон; среднюю и p95 ошибку оси/концов; ложную длину стен; число ложных дуг; долю свободных концов; качество T/L/X-узлов; число замкнутых помещений;
- разделить корпус на `development` и неизменяемый `holdout`, чтобы подбор порогов не проводился на выпускной выборке;
- расширить синтетический генератор негативными слоями: текст, размерные цепочки и стрелки, штриховка разных углов/шагов, мебель, лестницы, цветные рукописные пометки, шум, тени, размытие, JPEG-артефакты, перспектива и неполный кадр;
- подготовить разрешённый набор реальных сканов/фотографий с ручной эталонной разметкой. Закрытые планы допускаются в локальном/private benchmark, публичный набор содержит только разрешённые или синтетические данные;
- сохранить текущий проблемный план как обязательную локальную регрессию: отсутствие «спагетти», отсутствие массовых ложных дуг и корректный отказ при обрезанном контуре.

Выход этапа:

- машинно-читаемый JSON и Markdown-отчёт с per-case и aggregate-метриками;
- baseline текущей `v0.2.0`, который ожидаемо не проходит фотографический gate;
- CI запускает быстрый smoke-набор на каждый PR, полный holdout benchmark — перед релизом и при изменении распознавателя.

### Этап 23 — подготовка изображения и семантические маски · P0

Задачи:

- после crop/perspective выполнять устранение теней, нормализацию фона/контраста и несколько бинаризаций для тонких и толстых штрихов; не разрушать исходную подложку;
- выделять цветные пометки в HSV/Lab и формировать отдельную `annotationMask`; автоматическое удаление разрешать только при высокой цветовой отделимости, иначе показывать предложение пользователю;
- локализовать текст и числа до геометрического анализа с помощью OCR-boxes и connected-component признаков, расширять маску на обводку символов;
- находить размерные цепочки как сочетание тонкой линии, выносных линий, стрелок/засечек и соседнего числового текста; хранить их для OCR-размеров, но исключать из кандидатов стен;
- находить регулярную диагональную штриховку по доминирующему углу, повторяемому шагу и области заполнения; удалять штрихи только внутри подтверждённой hatch-области;
- отделять контур листа, рамку изображения и линии, оборванные границей кадра;
- выводить диагностические слои `background/text/dimensions/hatch/annotations/geometry` в тестовый snapshot и опциональную панель мастера.

Проверка:

- unit-тесты каждой маски на чёрно-белых и цветных вариантах;
- golden-image тесты с допустимым процентом расхождения маски;
- реальные стены, включая диагональные, не должны удаляться вместе со штриховкой;
- при отключённых OCR-подсказках геометрическая text-mask продолжает работать.

### Этап 24 — прямые стены, толщина и узлы · P0

Задачи:

- использовать Hough/LSD только как генератор коротких граней, а не готовых стен;
- объединять грани по углу, близости, непрерывности и поддержке пикселями; оценивать покрытие и остаточную ошибку;
- строить ось стены из пары параллельных граней с постоянной толщиной в метрах после калибровки; хранить измеренную толщину и диапазон её устойчивости;
- для однолинейных перегородок ввести отдельный классификатор: допустимый стиль штриха, подтверждённые T/L/X-соединения и отсутствие признаков размера/штриховки;
- учитывать несколько доминирующих направлений как prior, но не принуждать реальные диагональные стены к горизонтали/вертикали;
- аналитически строить T/L/X-пересечения, соединять только малые разрывы и запрещать продление через явные проёмы;
- при плиточной обработке объединять свидетельства в overlap-зоне до построения стен, чтобы не создавать дубли.

Проверка:

- отдельные тесты для двойных граней, тонких перегородок, оконных/дверных разрывов, диагональных стен, размерных линий и hatch-негативов;
- ложная длинная линия без второй грани и топологической поддержки не становится зелёной стеной;
- ошибка оси и толщины измеряется benchmark-командой в метрах.

### Этап 25 — дуговые стены, двери и окна · P0/P1

Задачи:

- убрать общий `HoughCircles → wall arc` из основного пути; оставить его только как ограниченный генератор гипотез либо удалить после сравнения benchmark;
- выделять связные контуры и аппроксимировать дуги RANSAC/robust circle fit с ограничением остаточной ошибки и непрерывной пиксельной поддержкой;
- подтверждать дуговую стену двумя концентрическими дугами с общим центром, согласованной толщиной и совместимыми концами; одиночную дугу считать слабым кандидатом;
- распознавать дверь только по совокупности `разрыв host wall + полотно + pivot + дуга допустимого радиуса`; отдельная окружность либо цветная пометка дверью не является;
- распознавать окно как геометрию внутри host wall с согласованным разрывом и параллельными элементами, а не по OCR-слову;
- сохранять касательную ориентацию проёма на настоящей дуговой стене;
- ввести независимые confidence и пороги для `curved-wall`, `door-swing`, `window`.

Проверка:

- отрицательные тесты на цифры `0/6/8/9`, красные окружности, винтовые/обычные лестницы и пересечения линий;
- положительные тесты на четверть круга двери, дуговую внешнюю стену и проём в дуговой стене;
- число ложных дуг является отдельным жёстким release-gate.

### Этап 26 — оптимизация архитектурного графа и калибровка confidence · P0

Задачи:

- формировать несколько гипотез графа и оценивать их по пиксельной поддержке, постоянству толщины, качеству узлов, непрерывности, проёмам и согласованности с доминирующими направлениями;
- штрафовать необъяснимые пересечения, изолированные сегменты, чрезмерное число дуг, дубли, очень короткие ветви и линии, проходящие сквозь подтверждённые помещения;
- не штрафовать честные свободные концы на границе обрезанного кадра, но помечать проект как неполный;
- калибровать итоговый confidence на development-корпусе и проверять calibration error на holdout; цветовые границы `green/yellow/red` выбирать по измеренным precision, а не вручную;
- добавить `RecognitionQualityReport`: полнота кадра, плотность кандидатов, доля свободных концов, доля изолированной длины, количество дуг, ожидаемая ручная трудоёмкость и причины отказа;
- определить fail-safe правила на основании benchmark. При «candidate explosion», плохой топологии либо некалиброванной уверенности отключать пакетное принятие и не позволять результату выглядеть успешным;
- комнаты вычислять только после оптимизации и пользовательского принятия; оптимизатор не дорисовывает отсутствующие стены ради замыкания.

Проверка:

- графовые unit-тесты и property-based тесты порядка/поворота/масштаба;
- одинаковый вход и параметры дают детерминированный результат;
- проблемная фотография завершается ограниченным числом объяснимых кандидатов либо понятным отказом, но не сотнями зелёных примитивов.

### Этап 27 — безопасная проверка результата и диагностический UX · P1

Задачи:

- заменить «Принять зелёные» на принятие проверенной связной цепочки/помещения; глобальная команда доступна только при пройденном `RecognitionQualityReport`;
- показывать отдельными переключаемыми слоями прямые стены, дуговые стены, двери/окна и исключённую графику;
- по выбранному кандидату объяснять confidence: покрытие граней, толщина, связность, topology score и причины штрафа;
- при плохом результате показывать конкретное действие: поправить четыре угла, обрезать лист, исключить область штриховки, выбрать профиль «фото с пометками» или перейти к ручной трассировке;
- добавить профили `Векторный PDF / Чистый скан / Фото / Фото с пометками`, оставив расширенные параметры доступными отдельно;
- добавить массовое отклонение выделенной областью и принятие/отклонение связного компонента;
- ограничить число одновременно рисуемых низкоуверенных кандидатов и применить viewport-отрисовку, не теряя их в данных;
- перед созданием проекта показывать сводку: принято стен/проёмов, свободные концы, незамкнутые области и оценку надёжности.

Проверка:

- component/integration-тесты quality-fail и quality-pass сценариев;
- ни один цвет или batch-action не обещает точность, которую не подтверждает calibrated confidence;
- ручные accept/reject/edit остаются атомарными Undo/Redo-транзакциями.

### Этап 28 — выпускные проверки, производительность и документация · P0

Обязательные release-gates:

| Категория | Метрика |
|---|---|
| Векторный PDF | F1 стен ≥ 0,98; метрическая ошибка ≤ 0,02 м |
| Чистый скан | F1 стен ≥ 0,90 при допуске 0,05 м; F1 проёмов ≥ 0,75 |
| Фотография | F1 стен ≥ 0,80 при допуске 0,10 м; F1 проёмов ≥ 0,60 |
| Все категории | отсутствие повреждения проекта при сбое/отмене; детерминированный результат; ручное доведение до валидного графа |
| Катастрофические ошибки | ни один holdout-кейс не создаёт неконтролируемый «спагетти»-граф; quality-fail блокирует пакетное принятие |
| Кривые/проёмы | отдельно публикуются precision/recall/F1 и число ложных дуг на изображение |
| Топология | отдельно публикуются dangling-end rate, precision/recall узлов и число корректно замкнутых помещений |

Дополнительные проверки:

- установить измеримые бюджеты времени и peak memory после baseline на целевой Windows x64 машине; регрессия более 20% требует объяснения;
- прогнать frontend unit/integration, Rust, lint/typecheck/build, быстрый benchmark и полный holdout benchmark;
- выполнить ручной offline smoke на чистой Windows 10/11: фото → crop/perspective → калибровка → анализ → исправление → 2D/3D → сохранение/повторное открытие;
- обновить `PRODUCT_SPEC`, `ACCEPTANCE_CRITERIA`, `ARCHITECTURE_DECISION`, `QA_REPORT`, руководство пользователя и release notes фактическими алгоритмами и измеренными результатами;
- не отмечать accuracy-gate выполненным по визуальному smoke, числу unit-тестов или структурному validator корпуса.

### Рекомендуемая последовательность поставки

1. **Safety hotfix:** ограничить/отключить ложные raster-дуги, ввести quality-fail и запрет пакетного принятия при candidate explosion. Это уменьшает вред, но не считается улучшением F1.
2. **Benchmark foundation:** этап 22 до дальнейшей настройки алгоритма.
3. **Raster precision:** маски этапа 23 и двойные грани/узлы этапа 24.
4. **Topology и confidence:** этап 26; только после него возвращать безопасное пакетное принятие.
5. **Curves/openings:** этап 25 с отдельными метриками, не смешивая их с прямыми стенами.
6. **Review UX и релиз:** этапы 27–28, документация и новый Windows-релиз с updater-артефактами.

### Основные риски и способы снижения

- **Text-mask удаляет часть стены:** сохранять несколько каналов признаков, использовать OCR-box только как признак и проверять непрерывность/толщину до окончательного удаления.
- **Hatch-filter удаляет диагональную стену:** требовать периодичность и область заполнения; подтверждённая двойная грань стены имеет приоритет над hatch-mask.
- **Тонкие перегородки не имеют двух граней:** отдельный классификатор с сильной топологической поддержкой и более низким confidence до проверки.
- **Topology optimizer «галлюцинирует» замыкание:** запрещено создавать геометрию без пиксельного/векторного свидетельства; допускается только небольшой snap существующих концов.
- **Реальный корпус слишком мал или закрыт:** отделить private holdout от публичного синтетического корпуса и публиковать агрегированные метрики без исходных закрытых планов.
- **Рост времени анализа:** раннее маскирование сокращает число геометрических гипотез; тяжёлые стадии запускаются по необходимости и остаются отменяемыми в worker.
- **Подгонка под один предоставленный план:** пороги принимаются только по development-набору и подтверждаются неизменяемым разнородным holdout.

### Условия завершения плана

- полный benchmark воспроизводимо запускает production pipeline и публикует per-case результаты;
- проблемная фотография больше не создаёт сотни зелёных линий/дуг: выдаётся компактный редактируемый граф либо честный quality-fail;
- все пороги `PRODUCT_SPEC` подтверждены holdout-отчётом;
- пользователь способен исправить оставшиеся ошибки без удаления сотен примитивов по одному;
- документация и Windows EXE/updater обновлены только после прохождения всех обязательных gates.

## 3. Результаты обследования исходного состояния

### 3.1 Репозиторий и окружение на момент первичного обследования

- В проекте пока нет каркаса приложения и `package.json`.
- Git не инициализирован. До первого крупного изменения нужно выполнить `git init` и сохранить исходный пакет отдельным baseline-коммитом; это действие выполняется только после согласования плана.
- Node.js 22.17.0, pnpm 10.33.2 и npm 10.9.2 доступны.
- `rustc`, Cargo и `cl.exe` сейчас не обнаружены. До сборки Tauri потребуется Rust MSVC toolchain и компоненты Visual Studio Build Tools для разработки настольных приложений C++.

После согласования плана окружение подготовлено: Git инициализирован, baseline сохранён, Rust/Cargo установлены, а существующие Visual Studio C++ Build Tools подтверждены успешной нативной сборкой Tauri 2.

### 3.2 Базовая геометрия

- SVG имеет `viewBox="0 0 23569.5996 2752.6399"`.
- Legacy использует `UPM = 377.952755906`, поэтому логический размер плана составляет примерно `62,3612 × 7,2830 м`.
- SVG содержит 7 952 `path`, 346 групп `.plan-label` и 1 262 `use`. Текст преобразован в векторные глифы, обычных SVG-элементов `<text>` в базовом плане нет.
- Геометрия и подписи уже разделены на `#basePlanGeometry` и `#basePlanLabels`.
- У каждой группы подписи есть `data-cx`, `data-cy` и `data-label`; это позволяет компенсировать поворот холста вокруг центра конкретной подписи.
- Среди меток присутствуют размеры, отметки высот, окна, радиаторы, ступени, перегородки и вентиляция.
- PDF состоит из одной очень широкой страницы. Его размеры и SVG совпадают с коэффициентом 4:1 по обеим осям, а визуальная структура соответствует: лестница слева, длинная последовательность помещений, окна, радиаторы, перегородки, вентиляция, размерные цепочки и высотные отметки.

### 3.3 Реализованное поведение legacy v6

- Одна страница с боковой панелью и SVG-холстом.
- 12 шаблонов: `pc1`, `pc2`, `pc5`, диван, кресло, стол, консольная зона, ресепшн, бар, серверная стойка, перегородка и свободная зона.
- Положение и размеры предметов хранятся в метрах; SVG-координаты вычисляются через `UPM`.
- X/Y предмета — координаты центра. Положительное направление X — вправо, Y — вниз. Положительный SVG-угол визуально вращает по часовой стрелке.
- Есть выбор одного предмета, перемещение, восемь маркеров размера, свободное вращение, шаг 15° с Shift, точные поля X/Y/ширины/глубины/угла, ±90°, дублирование и удаление.
- Есть зум колесом, панорамирование, вписывание плана, поворот холста на 90°, сетка 0,5 м и привязка 0,1 м.
- Базовый план не принимает pointer events. Подписи плана компенсируют поворот холста; подписи предметов вынесены за внутреннюю группу вращения предмета.
- История — полные JSON-снимки, максимум 80 состояний. Перетаскивание фиксируется на `pointerup` одной записью.
- Состояние v6: `{ version, base, canvasAngle, objects }`.
- Автосохранение выполняется только в `localStorage`, причём ошибки скрываются.
- JSON сохраняется браузерным download и открывается через `<input type=file>`; есть экспорт SVG.

### 3.4 Разрывы между legacy и требованиями

- Только `selectedId`: нет множественного выделения, общей рамки и групп.
- Нет слоёв, блокировки предметов и отдельной видимости подписи на уровне объекта.
- Нет рамочного выделения, `Ctrl+A`, режима группы и групповых трансформаций.
- История короче требуемых 100 операций и не имеет явной модели транзакций/dirty-state.
- Нет системных файловых диалогов, атомарной записи, списка недавних файлов, восстановления после сбоя и предупреждения о несохранённых изменениях.
- Ошибки `localStorage` проглатываются; повреждённый файл обрабатывается только минимально.
- Настройки сетки, привязки, видимости и контраста не входят в legacy JSON.
- Нет отключения `F5`, `Ctrl+R`, `Ctrl+P`, браузерного зума, стандартного контекстного меню и боковой навигации мыши.
- `Пробел + ЛКМ` не реализован.
- В legacy `Shift + стрелка` двигает на 0,5 м, что противоречит спецификации «точный малый шаг». В новой версии принимается: обычная стрелка — 0,1 м, `Shift + стрелка` — 0,01 м.

## 4. Архитектурные решения

### 4.1 Frontend: React + Vite + TypeScript

Выбирается React поверх Vite, а не полностью vanilla DOM.

Обоснование:

- интерфейс имеет много согласованных состояний: пустое/одиночное/множественное выделение, mixed-поля, режим группы, доступность команд, dirty-state и ошибки файлов;
- декларативные компоненты уменьшают риск рассинхронизации боковой панели, панели инструментов и холста;
- React используется только как слой представления; геометрия, модель проекта, команды, миграции и сериализация остаются обычными TypeScript-модулями;
- тяжёлый базовый SVG загружается один раз и не пересоздаётся React при каждом движении указателя;
- отдельная библиотека глобального состояния на первом этапе не нужна: достаточно собственного `EditorStore` с чистым reducer/command API и подпиской через `useSyncExternalStore`;
- Vite официально поддерживается Tauri для SPA, а React входит в официальные шаблоны Tauri.

Зависимости должны быть минимальны и зафиксированы lock-файлом. Плановый набор:

- runtime: React, React DOM, Tauri API и dialog/window-state plugins;
- runtime-валидация файлов: Zod либо эквивалентный компактный schema validator; окончательная версия фиксируется lock-файлом на этапе 1;
- development: TypeScript, Vite, ESLint, Vitest, jsdom, Testing Library;
- desktop E2E на позднем этапе: WebdriverIO с Tauri service.

Не использовать UI-kit и CSS-in-JS в MVP: нативных контролов и локальных CSS-модулей достаточно, а лишний UI-фреймворк усложнит offline bundle и визуальную стабильность.

## 5. Модель данных

### 5.1 Постоянное состояние проекта

```ts
type ObjectId = string;
type GroupId = string;
type LayerId = string;

interface ProjectState {
  projectId: string;
  basePlan: BasePlanRef;
  canvas: CanvasSettings;
  layers: Layer[];
  objects: PlanObject[];
  groups: ObjectGroup[];
}

interface PlanObject {
  id: ObjectId;
  type: ObjectType;
  name: string;
  xM: number;
  yM: number;
  widthM: number;
  depthM: number;
  rotationDeg: number;
  layerId: LayerId;
  locked: boolean;
  labelVisible: boolean;
  style?: { fill?: string };
  properties?: { seats?: number };
}

interface ObjectGroup {
  id: GroupId;
  name: string;
  objectIds: ObjectId[];
  locked: boolean;
}
```

Инварианты:

- все ID уникальны и стабильны;
- один объект входит максимум в одну группу;
- вложенные группы запрещены форматом v1;
- группа содержит минимум два существующих объекта;
- `widthM` и `depthM` конечны и не меньше 0,1 м;
- координаты конечны, но намеренно не обрезаются по границам плана;
- углы нормализованы в диапазон `[0, 360)`;
- порядок массива `objects` задаёт z-order внутри слоя;
- базовый план — отдельный системный слой и не является `PlanObject`.

X/Y задают центр предмета в неповёрнутой системе базового плана. Это сохраняет legacy-совместимость и делает массовое изменение размеров предсказуемым: размер меняется вокруг центра, если пользователь явно не тянет конкретный маркер.

### 5.2 Временное состояние редактора

Не записываются в `.clubplan`:

- выделение;
- hover и активный handle;
- режим текущего pointer-жеста;
- `groupEditId`;
- камера: экранный pan и zoom;
- Undo/Redo stack;
- dirty/saved revision;
- открытые панели, фокус и временное значение поля ввода.

```ts
type SelectionTarget =
  | { kind: "object"; id: ObjectId }
  | { kind: "group"; id: GroupId };

interface EditorSessionState {
  selection: SelectionTarget[];
  groupEditId: GroupId | null;
  camera: { panXpx: number; panYpx: number; zoom: number };
  interaction: InteractionState;
}
```

На верхнем уровне клик по участнику группы разрешается в target группы. В режиме редактирования группы тот же клик разрешается в target отдельного объекта. Все команды сначала раскрывают targets в уникальное множество object IDs, поэтому один объект нельзя случайно трансформировать дважды.

### 5.3 Семантика выделения

- ЛКМ: заменить выделение одним target.
- `Shift + ЛКМ`: toggle target.
- ЛКМ по пустому месту или `Esc`: очистить выделение; в режиме группы первый `Esc` выходит на уровень группы, следующий снимает выделение.
- `Ctrl+A`: выбрать все незаблокированные top-level targets на видимых слоях.
- Рамка: выбрать объекты, чья трансформированная геометрия пересекает рамку; `Shift + рамка` добавляет/toggle согласно отдельным тестам UX.
- Общая рамка строится по объединению world-space углов всех раскрытых объектов.
- Перетаскивание любого target в текущей выборке перемещает все раскрытые объекты на один world-space вектор.

### 5.4 Mixed-state и массовые свойства

Агрегатор возвращает для каждого поля один из результатов:

```ts
type AggregateValue<T> =
  | { kind: "uniform"; value: T }
  | { kind: "mixed" }
  | { kind: "not-applicable" };
```

Правила:

- ширина/глубина задаются каждому объекту отдельно, центры не меняются;
- абсолютный угол заменяет угол каждого объекта;
- ±90° добавляет угол каждому объекту относительно его текущего угла;
- слой, блокировка и видимость подписи применяются всем выбранным объектам;
- изменение одного поля для всей выборки — одна команда и одна запись Undo;
- ввод из mixed-state не должен временно подставлять значение первого объекта.

### 5.5 Группы

- `Shift + ПКМ` по выбранному незаблокированному объекту при выборе минимум двух незагруппированных объектов создаёт группу.
- `Ctrl+G` и контекстное меню вызывают ту же команду.
- Если выбор содержит существующую группу, группировка недоступна: вложенные группы в MVP запрещены.
- Центр поворота группы — центр axis-aligned bounding box всех трансформированных углов участников на момент начала операции.
- Поворот группы пересчитывает позиции участников вокруг фиксированного pivot и добавляет угол каждому предмету.
- Перемещение, поворот, дублирование, блокировка и удаление группы атомарны.
- Дублирование создаёт новые object IDs и новый group ID.
- Удаление группы удаляет группу и её участников; разгруппировка удаляет только запись группы.
- Двойной клик или команда «Редактировать группу» входит в режим группы; `Esc` выходит; `Ctrl+Shift+G` разгруппировывает.
- Группа и порядок `objectIds` сохраняются в `.clubplan`.

## 6. Координаты, камера и подписи

### 6.1 Канонические системы координат

1. **Project/world** — метры, начало в левом верхнем углу исходного плана, Y вниз.
2. **Plan SVG** — `world × UPM`, где `UPM = 377.952755906`.
3. **Rotated scene** — plan SVG после поворота холста вокруг `(PLAN_W/2, PLAN_H/2)`.
4. **Screen** — rotated scene после camera scale и translate.

Все конверсии реализуются чистыми функциями и матрицами. Pointer-координата проходит обратные преобразования в строгом порядке: inverse camera → inverse canvas rotation → деление на UPM. В DOM нельзя размазывать собственные варианты этих формул.

### 6.2 Камера и поворот холста

- Zoom ограничивается проверяемым диапазоном, ориентировочно 1–400% legacy camera scale.
- Zoom относительно курсора сохраняет world-point под указателем.
- Панорамирование: средняя кнопка или `Пробел + ЛКМ`; пустой ЛКМ может сохранить legacy-панорамирование, если не начинается рамочное выделение.
- «Вписать план» использует bounds четырёх углов после поворота 0/90/180/270.
- Canvas rotation хранится в проекте; camera pan/zoom — только в сессии.
- Сетка задаётся в метрах: крупная линия 0,5 м, snap 0,1 м.

### 6.3 Вертикальное положение и читаемость подписей

Базовая геометрия и подписи монтируются разными группами. Для каждой `.plan-label` сохраняется исходная трансформация глифов, а поверх неё применяется компенсация `-canvasRotation` вокруг `data-cx/data-cy`. Это возвращает подпись к исходной ориентации при 90/180/270°, не меняя её привязку к плану.

Подпись предмета находится рядом с объектом, но вне группы внутреннего вращения формы. Она компенсирует canvas rotation, поэтому остаётся читаемой при вращении предмета и холста. Отдельно проверяются горизонтальные и исходно вертикальные подписи, чтобы компенсация не меняла смысл их базовой ориентации.

## 7. Undo/Redo и транзакции

История строится на явных `EditorCommand`, а не на DOM-событиях.

```ts
interface EditorCommand {
  id: string;
  label: string;
  apply(project: ProjectState): ProjectState;
  revert(project: ProjectState): ProjectState;
}
```

Допускается реализация `before/after` patch внутри команды, но базовый SVG никогда не входит в снимки. История ограничивается минимум 100 завершёнными пользовательскими транзакциями.

Правила транзакций:

- pointer move обновляет только preview; одна команда фиксируется на `pointerup`;
- отменённый pointer gesture ничего не добавляет;
- move выборки, resize, group rotate, массовое поле, group/ungroup, duplicate и delete — по одной команде;
- изменение canvas rotation — одна команда;
- выбор, pan, zoom, hover и вход в group edit mode не входят в историю проекта;
- новая команда после Undo очищает redo branch;
- открытие/создание проекта сбрасывает историю и selection;
- dirty-state сравнивает history revision с saved revision, а не весь JSON;
- Undo до сохранённой revision снимает признак несохранённых изменений.

### В файл не входят

- selection и group edit mode;
- zoom/pan камеры;
- Undo/Redo;
- текущий путь к файлу и recent list;
- recovery/autosave metadata;
- временные ошибки и UI-фокус.

### Валидация и загрузка

- Сначала JSON parse и schema validation, затем проверка ссылочной целостности и числовых инвариантов.
- Неизвестная будущая `formatVersion` не открывается молча: показывается понятная ошибка о более новой версии.
- Повреждённый файл не заменяет текущий проект: новый state публикуется только после полной успешной проверки.
- Допускаются предупреждения с безопасной нормализацией углов/legacy IDs, но не скрытая потеря объектов.
- Round-trip `decode(encode(project))` должен сохранять модель с заданной точностью.

## 9. Миграция legacy JSON v6

Legacy определяется по `version === 6` и массиву `objects`, либо по отсутствию `format` при наличии совместимого списка объектов.

Маппинг:

| Legacy | `.clubplan` v1 |
|---|---|
| `canvasAngle` | `canvas.rotationDeg` |
| `object.id` | `object.id`, с устранением дубликатов |
| `type` | `type` |
| `label` | `name` |
| `x`, `y` | `xM`, `yM` |
| `w`, `h` | `widthM`, `depthM` |
| `angle` | `rotationDeg` |
| `fill` | `style.fill` |
| `seats` | `properties.seats` |
| отсутствует | `layerId="furniture"`, `locked=false`, `labelVisible=true` |

Правила:

- известные `type/kind` сопоставляются библиотеке; неизвестный тип сохраняется как безопасный custom object с legacy metadata;
- non-finite числа отклоняются, размеры меньше 0,1 м нормализуются только с явным предупреждением;
- legacy `meta.planWidth`, `planHeight` и `unitsPerMeter` используются для диагностики, но не заменяют актуальный base-plan;
- legacy v6 не содержит групп, поэтому `groups=[]`;
- исходный JSON не перезаписывается; после импорта предлагается «Сохранить как `.clubplan`»;
- `localStorage` браузерной версии автоматически не переносится. Пользователь должен экспортировать JSON из legacy, затем импортировать файл в desktop-приложении;
- ограничения миграции документируются в `docs/LEGACY_IMPORT.md` на этапе 4.

Фикстуры: валидный пустой v6, все 12 типов, неизвестный тип, дублирующиеся ID, отрицательные/нулевые размеры, неверный JSON, отсутствующий `objects`, будущая версия `.clubplan`.

## 10. Файлы, автосохранение и безопасность

### 10.1 Явное сохранение

- `@tauri-apps/plugin-dialog` отвечает только за системный выбор пути.
- Узкий Rust-адаптер читает UTF-8 проект и пишет его атомарно: временный файл в той же папке → flush/sync → replace/rename.
- При ошибке текущий файл и открытый проект остаются нетронутыми; пользователю показывается русское сообщение с путём и причиной без внутреннего stack trace.
- Перед заменой существующего файла можно использовать краткоживущую `.bak` только внутри атомарной операции; остатки обрабатываются при следующем запуске.
- Tauri capabilities разрешают только нужные диалоги и команды; произвольный shell и сеть не включаются.

### 10.2 Recovery autosave

- Recovery-файл хранится в App Local Data, а не рядом с пользовательским проектом.
- Autosave создаётся после debounce и только при dirty-state.
- Autosave не меняет saved revision и не считается явным сохранением.
- При старте предлагается восстановить более свежий recovery snapshot; отказ не удаляет его до подтверждения.
- После успешного явного сохранения соответствующий recovery snapshot удаляется.
- Recent files и window state хранятся отдельно от `.clubplan`.

### 10.3 Offline и CSP

- Все шрифты, стили, SVG и runtime assets входят в bundle.
- CSP разрешает только локальные источники, необходимые Tauri IPC; внешние `http/https` не нужны основной работе.
- Не использовать CDN, web-font загрузчики, телеметрию и auto-update в MVP.

### Этап 14 — подписанные автоматические обновления Windows и выбор размеров ✅

Цель — обновлять установленный Club Planner из GitHub Releases без ручного скачивания нового установщика, не нарушая автономную основную работу и не подвергая риску несохранённый проект.

План реализации:

1. Подключить официальные Tauri 2 plugins `updater` и `process`, включить только разрешения проверки/загрузки/установки и перезапуска главного окна.
2. Настроить HTTPS endpoint `releases/latest/download/latest.json`, `createUpdaterArtifacts: true` и публичный minisign-ключ. Закрытый ключ хранить только в GitHub Actions secrets; потеря или публикация ключа считается блокирующим инцидентом.
3. Выделить frontend-адаптер обновлений с явными состояниями: недоступно, ожидание, проверка, актуальная версия, обновление найдено, загрузка, установка и ошибка. Нативные модули загружать динамически только в Tauri runtime, чтобы web-сборка и тесты не запускали updater.
4. Проверять обновления один раз после старта без навязчивого сообщения при отсутствии сети. Установка начинается только после явного действия пользователя; доступна и ручная команда «Проверить обновления».
5. Перед установкой записывать recovery-копию грязного проекта. Показывать версию, примечания к релизу, загрузочный прогресс и понятную русскую ошибку с возможностью повторить.
6. Обновить release workflow: передать signing secrets в Tauri build, публиковать подписанный updater artifact и `latest.json` вместе с обычными installer/portable и SHA-256.
7. Поднять версию до `0.1.2`, обновить документацию, собрать installer и portable, опубликовать релиз и проверить его скачиванием, SHA-256, запуском и структурой `latest.json`.
8. Сделать постоянные размеры выбираемыми на холсте и в списке, всегда показывать фактическую длину, удалить выбранный размер через `Delete` одной Undo-транзакцией; selection размера не сериализовать.

Проверки:

- unit: редьюсер/форматирование прогресса и ошибок, защита от повторной параллельной проверки;
- integration: автоматическая проверка, ручная проверка, найденная версия, явная установка, recovery перед установкой, прогресс и ошибка;
- frontend gate: typecheck, lint, все Vitest, production build и rendered smoke без console error/warn;
- Rust gate: fmt, tests, Clippy;
- release gate: локальная подписанная Tauri build, NSIS/portable smoke, успешный GitHub Actions run, наличие `latest.json`, `.sig` и корректного `windows-x86_64` URL/signature.

Риски и решения:

| Риск | Мера | Gate |
|---|---|---|
| компрометация или потеря закрытого updater-ключа | ключ не попадает в Git/логи, хранится в GitHub secrets; публичный ключ фиксируется в приложении | secret scan + review config/workflow |
| потеря несохранённой работы при перезапуске | recovery записывается до download/install; установка не начинается автоматически | integration + native manual |
| отсутствие сети мешает работе | ошибка фоновой проверки не блокирует редактор; повтор доступен вручную | offline/manual smoke |
| подмена артефакта | обязательная проверка minisign-подписи Tauri и HTTPS endpoint | signed build + `latest.json` validation |
| два одновременных update-процесса | одна операция в полёте, повторные кнопки блокируются | integration test |
| первый updater-релиз не может доказать upgrade на самом себе | `v0.1.2` проверяет endpoint и отсутствие ложного обновления; полный `0.1.2 → 0.1.3` сценарий становится release-gate следующей версии | documented follow-up gate |

### Этап 15 — горячие клавиши, умное совмещение рядов, отражение и проходы ✅

Цель — ускорить повторяющиеся действия редактора, помогать точно совмещать два ряда одинаково расставленных похожих предметов в текущей видимой области, позволить зеркально отражать предметы/выборку без потери редактируемости, создавать проходы в перегородках и сохранять текущую планировку в PDF.

План реализации:

1. Перевести маршрутизацию команд на `KeyboardEvent.code` с fallback по `key`, чтобы `Ctrl+Z`, `Ctrl+G` и остальные сочетания работали при русской и английской раскладках; не перехватывать команды редактора внутри полей ввода.
2. Сохранить существующие `Ctrl+S/O/Z/Y/D/C/V/G/A`, `Delete`, `Esc`, `R` и стрелки; явно поддержать `Ctrl+Shift+Z` как альтернативный Redo.
3. Добавить `Ctrl+N` — новый проект, `Ctrl+E` — экспорт SVG, `Ctrl+L` — блокировать/разблокировать выборку, `Ctrl+0` и `F` — вписать план, `Ctrl+1/2/3` — 2D/3D/совмещённый вид, `M` — линейка. Показать полный список в сворачиваемой справке интерфейса и документации.
4. Выделить чистую геометрию распознавания ряда: минимум два предмета одного типа с близкими размерами и ориентацией, центры которых лежат на одной горизонтальной, вертикальной или диагональной оси.
5. Среди только видимых, незадействованных предметов искать параллельный ряд с тем же количеством и близким рисунком интервалов. При приближении совмещать центральные оси одним общим delta всей выборки, не меняя внутренние расстояния.
6. Показывать длинную пунктирную направляющую через оба ряда, маркеры центров и badge «Ряды на одной линии». Стены сохраняют высший приоритет; затем идут ряды, обычные объектные привязки и сетка. `Alt` отключает привязку, `Tab` перебирает кандидаты.
7. Добавить редактируемые флаги локального отражения `flipX/flipY` в модель предмета и формат проекта v3. Команды «Слева ↔ справа» и «Сверху ↕ снизу» отражают всю выборку относительно её общего центра, корректируют позиции и углы, сохраняют читаемыми подписи и работают через одну Undo/Redo-транзакцию. Горячие клавиши — `Shift+H` и `Shift+V`.
8. Применить отражение к 2D-отрисовке и SVG-экспорту; для симметричных 3D-параллелепипедов результат остаётся геометрически эквивалентным. Старые проекты v1/v2 загружаются с `flipX=false`, `flipY=false`, составные шаблоны и дубликаты сохраняют отражение.
9. Для одной выбранной перегородки добавить команду «Разделить»: пользователь задаёт ширину прохода, исходный предмет атомарно заменяется двумя независимыми частями по сторонам центрального проёма. Сохраняются толщина, высота, отметка, угол, слой, стиль, блокировка и членство в группе; новые части выделяются. Запретить проход, оставляющий часть короче 0,10 м.
10. Добавить автономный экспорт PDF: переиспользовать единый SVG-снимок проекта, преобразовать его локально в одностраничный PDF с альбомной ориентацией и текущими видимостью слоёв/сетки/подписей, выбрать путь через нативный Windows-диалог. Команда — `Ctrl+Shift+E`; ошибки преобразования/записи показываются пользователю.
11. Поднять версию до `0.1.3`, обновить требования/справку/формат/QA, выполнить полный frontend/Rust gate, rendered browser/PDF QA и подписанную Windows-сборку; опубликовать installer/portable/updater metadata и проверить публичные файлы.

Проверки:

- unit: горизонтальные, вертикальные и диагональные ряды, несовпадающие типы/интервалы, сохранение общего delta, ограничение видимой областью;
- integration: команды при русской раскладке, Undo/Redo, group/ungroup, lock/unlock, measure, fit и переключение видов; ввод текста не запускает команды;
- unit/integration: отражение одного предмета и группы по двум осям, инвариант общего центра/расстояний, повторная команда возвращает исходную геометрию, Undo/Redo и round-trip формата v3/v2 migration;
- unit/integration: разделение горизонтальной и повёрнутой перегородки, точная ширина прохода, минимальная длина частей, сохранение свойств/группы/выделения и Undo/Redo;
- Rust/integration/rendered: валидный PDF `%PDF`, одна страница, корректные MediaBox/ориентация и визуальное сравнение PNG-рендера с SVG без обрезки и нечитаемых подписей;
- rendered: перемещение ряда к другому ряду показывает направляющую/маркеры, фиксирует совмещение одной Undo-транзакцией и не оставляет console error/warn;
- release: `pnpm check`, Rust fmt/test/Clippy, подписанный Tauri build, portable/NSIS smoke, GitHub Actions и проверка `latest.json`/`.sig`.

Риски и решения:

| Риск | Мера | Gate |
|---|---|---|
| ложное распознавание случайного набора как ряда | одинаковый тип, допуски размеров/угла/коллинеарности и близкий рисунок интервалов | unit + rendered |
| привязка к предметам в другой комнате вне экрана | кандидаты ограничены пересечением с текущей видимой областью и видимыми слоями | viewport unit + rendered |
| конфликт ряда со стеной или сеткой | явный приоритет `wall → row → object → grid`, `Tab` и временное отключение через `Alt` | resolver tests |
| горячая клавиша портит ввод числа/имени | после блокировки опасных WebView-команд editor shortcuts не обрабатываются для input/textarea/select/contenteditable | integration |
| русская раскладка меняет `event.key` | физический `event.code` является основным идентификатором, `key` остаётся fallback для совместимости | integration с кириллическим `key` |
| отражение ломает повёрнутые предметы или зеркалит подписи | матрично корректировать позицию/угол и локальный флаг отражения, а подписи/handles держать вне reflected shape group | geometry + component + SVG tests |
| разделение создаёт нулевую часть или теряет групповую связь | валидировать доступную длину до команды, заменять ID в группе атомарно и выбирать обе новые части | command + integration tests |
| PDF теряет кириллицу или обрезает широкий план | преобразовывать SVG-текст в локальном desktop pipeline, сохранять aspect ratio в MediaBox и проверять рендер через Poppler | Rust + rendered PDF QA |

## 12. Тестовая стратегия

### 12.1 Unit-тесты TypeScript

- `units/matrix`: world↔SVG↔screen round-trip, zoom-at-point, inverse 0/90/180/270;
- `bounds`: повёрнутые прямоугольники, общая рамка, group pivot;
- `selection`: replace/toggle/clear/Ctrl+A, locked/hidden, group target resolution;
- `aggregate-properties`: uniform/mixed/not-applicable;
- `bulk edit`: индивидуальная W/H при сохранении центров, absolute и relative angles;
- `groups`: membership invariants, move, rotate, duplicate ID remap, delete, ungroup;
- `commands/history`: одна транзакция на gesture, branch after Undo, limit 100, saved revision;
- `serialization`: `.clubplan` round-trip, schema errors, future version;
- `legacy migration`: все fixture-классы из раздела 9;
- `labels`: compensation transforms и сохранение центров при 180°;
- `snap`: 0,1 м, disabled snap и малый keyboard step 0,01 м.

### 12.2 Component/integration frontend

- свойства single/multi selection;
- mixed input → commit всем;
- toolbar availability по selection/group edit/locked;
- keyboard command routing без срабатывания при вводе в поле;
- pointer state machine: move/resize/rotate/cancel;
- ошибочная загрузка не заменяет текущий документ;
- status/error banners и unsaved prompt;
- SVG overlay не содержит handles после export clone.

### 12.3 Rust tests

- атомарная запись и замена существующего файла;
- ошибка записи сохраняет исходный файл;
- UTF-8 read/write;
- ограничения размера входного файла;
- recovery file lifecycle и recent files;
- нормализация расширения `.clubplan` без повреждения имени.

### 12.4 Desktop E2E

Минимальные сценарии:

1. Запуск отдельного окна и наличие актуального плана.
2. Добавить предмет → переместить → Undo/Redo.
3. Выделить два предмета → массовая ширина → Undo.
4. Сгруппировать → повернуть → Save → Open → Ungroup.
5. Открыть повреждённый файл и сохранить текущую работу.
6. Горячие клавиши editor работают, браузерные действия заблокированы.

Native file dialogs в E2E по возможности обходятся через тестовый Tauri command/mock; отдельная ручная проверка подтверждает реальные системные диалоги.

## 19. Бэклог UX-точности и прикладного планирования (2026-08-21)

Цель направления: сократить путь от импортированного чертежа до проверяемой расстановки клуба или HoReCa-помещения, не превращая Club Planner в универсальный CAD/BIM.

### P0 — текущая реализация

- [x] Верхняя командная панель: Undo/Redo, выбор, панорамирование, линейка, вписать план, сетка, привязки и переключение 2D/3D.
- [x] Активный инструмент имеет заметное состояние, русскую подпись/tooltip и работает вместе с горячими клавишами.
- [x] Существующий постоянный размер выбирается на холсте и получает экранные ручки начала, конца и переноса всей линии.
- [x] Перетаскивание конца показывает новую длину в live-режиме; перенос средней ручки сохраняет длину.
- [x] Размер притягивается к вершинам/граням стен, проёмам, центрам и углам предметов, затем к сетке; `Alt` временно отключает привязки, `Shift` фиксирует горизонталь/вертикаль.
- [x] Один pointer-drag размера создаёт одну Undo/Redo-транзакцию; `pointercancel` и `Esc` не оставляют частичное изменение.
- [x] Выбранный размер перемещается стрелками, `Shift+стрелка` использует малый шаг 0,01 м.
- [x] Добавить unit/component/integration-тесты редактирования размера, привязок, live-preview и командной панели.
- [x] Обновить пользовательскую и продуктовую документацию после прохождения gate.
- [x] Собрать новый NSIS EXE после полного frontend/Rust gate и опубликовать подписанные updater-артефакты `v0.2.4` через release workflow.

### P0.1 — следующий вертикальный срез

- [ ] Ассоциативные якоря размера: свободная точка, вершина/ось/грань стены, край/центр проёма, угол/центр предмета.
- [ ] Автоматическое обновление ассоциативного размера при изменении геометрии и явное состояние «привязка потеряна».
- [ ] Ручка смещения подписи/размерной линии и точный числовой редактор длины/координат без скрытого изменения архитектуры.
- [ ] Постоянные направляющие и точки-направляющие с перемещением, блокировкой и удалением.
- [ ] Выровненные, горизонтальные, вертикальные, угловые и радиальные размеры; цепочки размеров.

### P0.2 — пустой проект, помещения, двери и массовая очистка импорта

Цель вертикального среза: новый пользователь начинает с чистого листа, может быстро построить прямоугольное помещение, поставить дверь точно на стену/перегородку и за один жест удалить шум распознавания на шаге проверки импорта.

- [x] Новый проект использует пустой лист без встроенного обмера, семантических стен, проёмов и высотных зон; импортированный или открытый старый проект сохраняет свой источник без изменений.
- [x] Пустой лист остаётся валидным самодостаточным `.clubplan` v4, имеет предсказуемые размеры рабочей области и не показывает старый чертёж при переключении видимости подложки.
- [x] Инструмент «Помещение» (`P`): ЛКМ в первом углу → drag → отпускание во втором углу; live-preview показывает четыре стены и размеры, `Shift` создаёт квадрат, `Esc`/`pointercancel` отменяет операцию.
- [x] Завершённый прямоугольник создаёт четыре принятые ручные архитектурные стены с общими вершинами одной Undo/Redo-транзакцией; помещение автоматически появляется в вычисляемом списке комнат и 3D.
- [x] Инструмент «Дверь» (`D`) подсвечивает ближайшую допустимую стену/перегородку и размещает проём шириной 0,9 м в точке клика; край проёма не выходит за торцы и не пересекает существующие проёмы.
- [x] Для архитектурной стены дверь создаётся как host-opening; для предмета-перегородки команда атомарно преобразует перегородку в две части вокруг проёма и создаёт дверь, визуально и семантически связанную с ним.
- [x] Дверь после установки доступна в 2D/3D, имеет дугу открывания и редактируемые ширину, высоту, направление и положение; операция установки является одной Undo/Redo-транзакцией.
- [x] На шаге 4 импорта drag по пустой области создаёт рамку пересекающего выделения: выбираются стены и дуги, которых рамка касается; `Shift` меняет состав выборки, одиночный клик сохраняется.
- [x] `Delete`/`Backspace` на шаге проверки отклоняет всё рамочное выделение одной review Undo-транзакцией; кнопки «Принять» и «Отклонить» применяются ко всей выборке.
- [x] Инструмент дуги на шаге 4 является одноразовым: начало → конец хорды → точка кривизны создают одну дугу, очищают временные точки и автоматически возвращают режим выбора.
- [x] Геометрия трёхточечной дуги выбирает проходящую через управляющую точку minor-дугу до 180° и не превращается в почти полный круг; коллинеарные и вырожденные точки дают понятную ошибку без частичного результата.
- [x] Выбранная ручная дуга получает три ручки: начало, конец и кривизна; drag любой ручки показывает live-preview, сохраняет общую топологию концов и коммитится одной review Undo-транзакцией.
- [x] `Esc`, повторное нажатие кнопки дуги или переключение инструмента всегда прекращают постановку и убирают временные точки/preview.
- [x] Добавлены unit-тесты пустого проекта, прямоугольной комнаты, установки двери/конфликтов проёмов и геометрии пересечения рамки; component-тесты pointer-flow дуги, рамки, Undo/Redo и массового отклонения.
- [x] Обновлены продуктовая документация, руководство и QA; frontend/Rust gates и rendered Browser QA пройдены, Windows portable/NSIS EXE `v0.2.5` собраны и проверены smoke-тестами.

Риски и проверки:

| Риск | Решение | Gate |
|---|---|---|
| старый встроенный план неожиданно появляется на пустом листе | отдельный пустой источник и явная проверка активного source перед отрисовкой bundled SVG | model + rendered test |
| drag помещения вызывает тяжёлые project updates | локальный SVG-preview, одна команда только на `pointerup` | component interaction test |
| дверь у торца или поверх другого проёма ломает геометрию | ограничение offset и проверка интервалов с безопасным зазором | architecture unit tests |
| разделённая предмет-перегородка теряет свойства/группу | единая команда сохраняет слой, высоту, угол, стиль и членство группы для обеих частей | command + Undo test |
| рамка импорта случайно двигает вершины | marquee стартует только по фону и имеет отдельный pointer-state | review component test |

### P0.3 — читаемая архитектура после импорта и патч `v0.2.6`

- [x] Добавить на верхнюю панель быстрый переключатель подложки и уменьшить её начальную непрозрачность для нового импортированного проекта.
- [x] После импорта явно сообщать количество созданных стен, перегородок и проёмов.
- [x] Добавить unit/component-тесты физической толщины, выбора, ручек, транзакции перемещения и переключателя подложки.
- [x] Пройти frontend/Rust gates, rendered Browser QA, собрать EXE и опубликовать подписанный updater-патч `v0.2.6`.

Риски и проверки:

| Риск | Решение | Gate |
